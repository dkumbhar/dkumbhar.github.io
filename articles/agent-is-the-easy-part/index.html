Field guide · Agentic AI system design

The agent is the easy part. The system around it is the job.

An engineer's guide to taking LLM agents from a demo that impresses a room to software that thousands of strangers can rely on: routing, tool contracts, memory, durable orchestration, evals, security and the operating discipline that ties them together.

01Why demos lie

Every agent demo has the same shape. Someone types a request, the model thinks out loud, a couple of tools fire, a tidy answer appears, and the room nods. Then the system meets real traffic, and a team that spent two weeks on the demo spends six months on everything the demo never had to deal with.

The reason is arithmetic. An agentic system is a chain of model calls, interleaved with tool calls, retrievals and state updates. Each step has its own probability of going right, and the probabilities multiply. A step that is right 98% of the time sounds excellent. Twenty of them in a row succeed together only about 67% of the time. The demo was one lucky run of a probabilistic process. Production is that process run a hundred thousand times a day.

It gets worse once you care about consistency rather than average success. Sierra's τ-bench introduced a metric called pass^k: the probability that an agent completes the same task correctly on all k independent attempts. If the per-run success rate is p, pass^k is roughly pk. An agent that succeeds 90% of the time has a pass^8 of about 43%. In the original τ-bench paper, the strongest model tested scored under 25% pass^8 on the retail domain. The metric is closer to what users experience, because a customer who asks for a refund needs it processed correctly every time they ask.

Production engineering is mostly about two jobs: replacing probabilistic steps with deterministic code wherever you can, and putting validation, retries, fallbacks and human review under the steps that remain.

DefinitionAn agentic AI system is production software in which a model pursues a goal over several steps: it breaks the goal down, chooses actions, calls tools, observes results, updates state and continues until a stopping condition. Its outputs change things in the world through APIs. That last property is what turns a chatbot problem into a distributed-systems problem.

02Workflow or agent? Choosing your autonomy

Anthropic's essay Building Effective Agents draws a useful line. In workflows, LLMs and tools are orchestrated through predefined code paths. In agents, the LLM itself directs the process and decides which tools to use and when. Between a single model call and a fully autonomous swarm there is a spectrum, and the right answer for most product features sits much further left than the hype suggests.

A good test: if you can draw the flowchart, write the flowchart. When a task's sequence is mostly known, such as "look up the order, check the refund policy, issue the refund, confirm," encode it as a pipeline or state machine and use the model only at the decision points that need language understanding. Save true agent loops for problems where you can't predict the number or order of steps in advance, like open-ended research, debugging, or investigating why a metric moved.

You set autonomy per action. One product can include a fully deterministic billing path, a routed support workflow and an autonomous research agent. Each should sit at the autonomy level its risk and its evals justify.

03A reference architecture

Figure 2 shows how the components fit together before the sections that follow take them one at a time. Your boxes may be one service or twelve, but each responsibility should exist somewhere you can point to.

Three structural ideas matter more than any single box. The model never touches the outside world directly: it proposes actions, and the tool gateway decides whether they run. Business rules live in code that can be unit-tested, so whether a refund is allowed is never inferred from a policy PDF. And observability sits under everything else, because in a probabilistic system you can't fix a failure you can't replay.

04The model layer: route, constrain, expect failure

The naive design uses the biggest model you can afford for every step. It works in the demo and then ruins your unit economics and your p95 latency. A single user request in a mature agent may involve intent classification, query rewriting, retrieval, planning, tool selection, argument generation, result interpretation, response generation and an evaluation pass. Most of those steps are easy.

Model routing sends each step, or each request, to the cheapest model that can handle it. The RouteLLM work (ICLR 2025) trained routers on preference data. On MT-Bench they kept about 95% of GPT-4's quality while sending only around 14% of queries to the strong model, a cost reduction of roughly 85%. Savings were smaller on harder benchmarks, about 45% on MMLU and 35% on GSM8K, so what you save depends on your traffic mix.

Routing only works if each step has a crisp output contract. Any output that feeds another system should be structured: a JSON Schema, a Pydantic model, a function call. Free-form prose that a downstream regex has to parse will eventually break that regex. For every model step, the design should answer three questions: which model, what contract, and what happens when the output is invalid?

from pydantic import BaseModel, Field
from typing import Literal

class BookingIntent(BaseModel):
    intent: Literal["book", "reschedule", "cancel", "question", "out_of_scope"]
    appointment_id: str | None = None
    preferred_dates: list[str] = Field(default_factory=list)   # ISO-8601, validated in code
    constraints: list[str] = Field(default_factory=list)       # "no mornings", "after lab results"
    confidence: float = Field(ge=0, le=1)

def classify(msg: str) -> BookingIntent:
    for model in ("small", "frontier"):                 # cascade
        try:
            out = llm(model, msg, response_format=BookingIntent, timeout=4)
            if out.confidence >= 0.75 or model == "frontier":
                return out
        except (ValidationError, Timeout, ProviderError):
            continue
    return BookingIntent(intent="out_of_scope", confidence=0)  # safe fallback
A small model handles the common case; the frontier model handles ambiguity ("I'm traveling next week, avoid mornings, and it has to be after my lab results"). Invalid output never travels downstream.

Treat every model call like a flaky upstream dependency, because that's what it is. Timeouts, rate limits, provider outages, malformed output and silent quality regressions after a provider update all need a handling path. Pin model versions explicitly. If you configure a fallback provider, give the fallback model its own eval run. An untested fallback is a second failure mode you haven't found yet.

05Tools are APIs with a very creative client

Tools are how agents act: database lookups, CRM updates, calendar bookings, payments, code execution, tickets, messages. Think of each tool as an API published for a client who is brilliant, tireless, occasionally confused, and possibly being manipulated by an attacker.

Every tool needs a precise name and description, typed input and output schemas, permission boundaries, timeout and retry behavior, and a structured error format. The most common mistake is the "do-what-I-mean" tool:

// ✗ Too open-ended: the model can smuggle anything into "instruction"
{ "name": "update_user",
  "parameters": { "instruction": { "type": "string" } } }

// ✓ Narrow, typed, auditable
{ "name": "update_user_field",
  "description": "Change ONE allow-listed profile field for the authenticated user.",
  "parameters": {
    "user_id":            { "type": "string", "pattern": "^usr_[a-z0-9]{12}$" },
    "field":              { "enum": ["display_name", "phone", "timezone"] },
    "new_value":          { "type": "string", "maxLength": 120 },
    "reason":             { "type": "string" },
    "source_request_id":  { "type": "string" },
    "idempotency_key":    { "type": "string" }
  },
  "x-risk": "low_write", "x-requires_confirmation": true, "x-timeout_ms": 3000 }

A tool should return a machine-readable result on success and a structured error on failure, such as {"error":"SLOT_TAKEN","retryable":false,"alternatives":[...]}, so the orchestrator can branch on it without asking a model to interpret a stack trace. Keep payloads small, because the model has to read every token a tool returns, you pay for each one, and a long result can confuse it. Paginate, filter and summarize at the tool boundary.

Tier your tools by blast radius

The over-tooled agent

As tool catalogs grow, selection accuracy drops sharply. In the RAG-MCP study, an LLM shown a very large catalog of MCP tools picked the right one only 13.6% of the time. When a retrieval step first narrowed the catalog to the most relevant candidates, accuracy rose to 43.1%, and prompt tokens fell by more than half. Treat tool descriptions as prompts that need testing. Group tools by namespace. Retrieve a small relevant subset per step rather than putting your entire integration surface into every call.

MCP and A2A

Two open protocols are standardizing how these pieces connect. The Model Context Protocol (MCP), released by Anthropic in November 2024 and donated to the Linux Foundation's Agentic AI Foundation in December 2025, defines how an agent discovers and calls tools, resources and prompts. Google's Agent2Agent (A2A) protocol, launched in April 2025 and moved to the Linux Foundation that June, defines how independent agents discover each other (via "Agent Cards") and hand off tasks without exposing their internals.

06Memory, state and context

This is where most agent codebases turn to mush, because "memory" gets used for four different things. Separate them early.

State is the execution context of the current workflow: which step we're on, what's been collected, which tools ran and what they returned, whether the user confirmed, and whether we passed or failed. It's structured, small and transactional. Memory is broader: conversation history, preferences, past actions, retrieved knowledge, summaries. It's large, fuzzy and retrieved selectively. Mixing the two means critical workflow facts end up as sentences in a chat log that the model may or may not re-read correctly.

A vector database is a poor default for workflow facts. If the question is "what's the current appointment ID?", answer it with a key lookup instead of a nearest-neighbor search over chat history.

Treat context as a budget

Long context windows tempt teams to put everything in, and the research says that backfires. Chroma's "context rot" study across 18 models found that performance degrades as input grows, even on simple retrieval tasks. Anthropic's guidance on context engineering frames the goal as finding "the smallest set of high-signal tokens" that maximize the chance of the desired outcome. The model has a limited amount of attention, and every irrelevant token spends some of it.

For long-running work, three techniques do most of the work. Compaction summarizes a conversation that's nearing its limit and restarts with the summary. SentinelOne reported about 86% fewer input tokens with no measurable quality loss on a malware-analysis harness. Context editing clears stale tool results the agent could re-fetch if needed. Structured note-taking means the agent writes durable notes, such as a plan, findings or a to-do list, to external memory and reads them back. Anthropic reported that context editing plus a memory tool improved an internal agentic-search eval by 39% over baseline, and cut token use by 84% in a 100-turn web-search eval.

The same discipline gives you a good privacy rule. If the rescheduling step needs an appointment ID and a list of open slots, it gets exactly that, and it does not get the patient's medical history "just in case". Data minimization helps security, compliance and model performance at the same time.

Designing memory writes

Teams think hard about reading memory and barely at all about writing it. Decide explicitly what the agent may remember, for how long, who can see it and how conflicts are resolved when a new fact contradicts an old one. Guard the write path. OWASP lists Memory & Context Poisoning (ASI06) among the top agentic risks, because one injected "remember that refunds over $500 are pre-approved" can contaminate every future session. Make long-term memory user-visible and user-deletable. Privacy law such as GDPR's right to erasure will require that anyway.

07Orchestration that survives failure

Orchestration is the control layer. It defines how a request moves from intake through intermediate steps and tool calls to a final output. You can build it with plain code, a graph framework like LangGraph, LlamaIndex Workflows, a durable workflow engine like Temporal, or a hand-rolled state machine. Whichever you pick, even an autonomous agent loop should run inside an explicit frame of states, transitions, budgets and exits.

Durable execution and idempotency

Real agents crash mid-run, get redeployed under load, and wait hours for an approval. Restarting from scratch wastes money, and worse, it repeats side effects. The fix borrowed from distributed systems is durable execution: persist the outcome of every step so a run resumes exactly where it stopped. Temporal, Restate, DBOS and Inngest provide this, as do LangGraph's checkpointers and several cloud "durable function" offerings.

Engines like Temporal checkpoint at the activity boundary, so a tool call that was in flight when a worker died will run again. If that tool charges a card, you've charged it twice. Every side-effecting tool therefore needs an idempotency key, derived from the workflow ID and step rather than generated fresh on each attempt, so the downstream system can deduplicate.

def execute_write(run: Run, step: str, tool: Tool, args: dict):
    key = sha256(f"{run.workflow_id}:{step}")          # stable across retries
    if (prior := run.ledger.get(key)):                  # already done? return it
        return prior
    policy.authorize(run.user, tool, args)                # deterministic, raises on deny
    run.budget.charge(tool.cost_estimate)                 # raises BudgetExceeded
    result = tool.call(args, idempotency_key=key, timeout=tool.timeout)
    run.ledger.put(key, result)                           # checkpoint before moving on
    return result

For multi-step operations that can partially succeed, such as booking the new slot and then failing to release the old one, design compensating actions (the saga pattern). Each write step registers its undo. If a later step fails irrecoverably, the orchestrator runs the compensations in reverse, or escalates to a human with a precise description of the half-finished state.

Loop guardsAgents fail in a characteristic way: they get stuck, calling the same search again and again with slightly different phrasing and burning tokens until something times out. Give every run hard limits on steps, tool calls, tokens or dollars, and wall-clock time. Add a repeat-call detector. When a guard trips, exit through a designed path such as a partial answer, a clarifying question or a handoff, instead of throwing an exception.

08When (and when not) to go multi-agent

Multi-agent architectures split work across specialists, such as a planner, retrievers, a coder, a reviewer and an executor, each with a defined role and input/output contracts. They're seductive because they mirror how human teams work. They're also where a lot of engineering effort goes to die.

Anthropic's write-up of its Research feature is the clearest public case for multi-agent setups. A lead agent plans and spawns three to five subagents that search in parallel with fresh context windows, and a separate pass verifies citations. It also shows when the pattern wins: breadth-first tasks that split into independent threads and whose combined information exceeds one context window. Anthropic notes that tasks where agents need shared context or have many dependencies, which includes most coding, benefit far less.

The MAST study ("Why Do Multi-Agent LLM Systems Fail?", NeurIPS 2025) annotated over 1,600 execution traces and grouped 14 failure modes into three families. System design issues include poor role specification and failing to recognize when the task is done. Inter-agent misalignment includes withheld information, ignored input and derailed conversations. Task verification failures are missing or wrong verification. Many of these are really specification problems. When agents talk to each other in free text, you've reintroduced every ambiguity you removed with tool schemas.

Start with one agent, measure, and split only when an eval shows a gain that justifies the token multiplier. You can borrow the best multi-agent ideas without the topology: write state to external memory before context fills, give subtasks self-contained descriptions, and verify high-stakes outputs with a separate pass. If you do split, route subagents by role to cheaper models. A bounded lookup doesn't need the orchestrator's frontier model. Also make sure the execution layer never blindly trusts the planning layer; OWASP lists both Cascading Agent Failures (ASI08) and Insecure Inter-Agent Communication (ASI07) as top agentic risks.

09Approval gates: the model proposes, code disposes

Not every action needs a human, but high-impact actions need gates. These include sending external email, deleting data, issuing refunds, canceling bookings, changing billing, updating systems of record, running code, placing orders and moving money. None of them should happen just because a model inferred that's what the user wanted.

Replit's July 2025 incident shows what happens without gates. During a publicized trial, its coding agent ran destructive commands against a live production database during an explicit code freeze, despite instructions to ask before making changes. It then misreported whether rollback was possible. Replit fixed it in the architecture: automatic separation of development and production databases, a planning-only mode, and better one-click restore. A model can ignore an instruction in its prompt, but it can't use a credential it was never given.

Two refinements make gates work in practice. First, watch for approval fatigue. If you gate everything, users click "yes" without reading, and OWASP's Human-Agent Trust Exploitation (ASI09) describes attackers who rely on exactly that. Gate by risk tier and show the concrete consequence ("This will refund $412.50 to card ending 4421"). Second, design the handoff to a human as carefully as the happy path. Pass the full trace and the half-finished state so the person picking it up never has to ask the customer to repeat themselves.

10Security: assume every token is hostile

LLMs receive instructions and data in the same channel. There's no hardware boundary between "system prompt" and "the web page we just fetched". So treat everything that reaches the model as potentially attacker-controlled until proven otherwise. That includes user messages (direct injection), retrieved documents and emails (indirect injection), tool outputs (poisoned data) and the model's own outputs (unsafe SQL, shell commands, HTML).

Because no classifier reliably detects injection, the strongest defenses are architectural. The Dual-LLM pattern uses a privileged model that sees only trusted input and can call tools, plus a quarantined model that reads untrusted content but has no tools. The privileged model handles the quarantined model's outputs as opaque variables and never follows them as instructions. Google DeepMind's CaMeL (2025) goes further. It turns the user's request into a small program, tracks the provenance of every value with capability labels, and enforces policies at each tool call, so untrusted data can never change control flow or flow to an unauthorized destination. In the AgentDojo benchmark it completed 67% of tasks with provable security. That's a capability trade-off, but the right one for high-stakes surfaces.

The OWASP GenAI Security Project's Top 10 for Agentic Applications (2026), published in December 2025 and built from real 2025 incidents, is the best current checklist for threat modeling:

OWASP pairs the familiar principle of least privilege with a newer one, least agency: limit not only what an agent can access, but how much freedom it has to act on that access without checking back. Five concrete rules follow from that:

  • Never execute raw model output. No SQL or shell commands straight from generated text. Generate parameters, not programs, or run generated code in a sandbox with no credentials, CPU, memory and time limits, a throwaway filesystem and an egress allow-list.
  • Keep secrets out of context entirely. The tool gateway attaches credentials. The model never sees them.
  • Act on behalf of the user instead of through a god-mode service account. Use OAuth-style delegated tokens scoped to the user and the task, so the agent's blast radius equals the user's permissions at most.
  • Isolate tenants everywhere, including caches and vector indexes. Cross-tenant leakage through shared retrieval is a common and embarrassing bug.
  • Rate-limit per user and per tenant. Attackers do run "denial of wallet" attacks, which simply drive up your inference bill.

11Evaluation that sees the whole trace

In traditional software, "no exception thrown" is a decent proxy for "worked". In agentic systems that proxy fails constantly. The model can return valid JSON that means the wrong thing, call the right tool with the wrong arguments, retrieve a stale policy, skip a confirmation, refuse a legitimate request or comply with a malicious one, all without a single error in your logs.

If you only grade the final answer, a polished reply built on the wrong refund policy scores as a success.

So evaluation has to happen at the trace level: grade each important step in the trajectory. Was the intent classified correctly? Did retrieval surface the right document? Was the right tool chosen, with correct arguments? Was policy respected? Was confirmation requested when required? Did the world end up in the right state? τ-bench judges success by comparing the final database state with the expected goal state instead of reading the conversation, and any agent that writes to a system should be graded the same way.

Build a scenario suite that reflects reality: happy paths, ambiguous requests, out-of-scope requests, tool failures, malicious inputs, partial information, policy edge cases and escalations. Run it as a regression gate whenever you change the model, a prompt, retrieval logic or a tool schema. Run each scenario several times and report pass^k alongside average accuracy, because a test that passes on one sample tells you little about a stochastic system. Use simulated users, an LLM playing the customer the way τ-bench does, to exercise multi-turn flows at scale.

In production, run sampled asynchronous evals on live traces, route high-signal user feedback (thumbs-down, escalations, "that's wrong") straight into an eval queue, and turn every real failure into a permanent regression test. LLM-as-judge is useful but imperfect. Calibrate it against human labels, watch it for drift, and never let it be the only check on a high-stakes workflow.

12Observability: make every run replayable

When an agent misbehaves, the first question is always "where did it go wrong?" Was it intent classification, retrieval, planning, tool selection, tool execution, policy validation or the final response? You can only answer that if every run records its full anatomy: model name and version, prompt version, step name, workflow and conversation IDs, tool names and arguments (with sensitive values masked), latency and time-to-first-token, tokens in and out, cost, retries, fallbacks, errors, user feedback and eval scores.

You don't need to invent a schema. OpenTelemetry's GenAI semantic conventions define a shared vocabulary under the gen_ai.* namespace. It includes operations such as chat, invoke_agent, execute_tool and embeddings, and attributes such as gen_ai.request.model and gen_ai.usage.input_tokens. Langfuse, Arize Phoenix, Braintrust, Datadog and others ingest them. Capturing prompt and response content is deliberately opt-in, because it so often contains personal data. Core model-call attributes are stable enough for production dashboards, while the agent-level conventions are still evolving.

Set retention policies for traces, logs and conversation archives, and mask personal data before it reaches your observability vendor. Your model provider, vector database, tracing platform and logging pipeline are all inside your data boundary, and an auditor will treat them that way.

13Cost and latency engineering

Cost and latency have to be designed in from the start, and together, because both scale with the number and size of model calls per request. A few levers account for most of the savings.

Route by difficulty, as Section 4 describes. Cap output tokens hard: output tokens are typically several times the price of input tokens and generated one at a time, so a two-sentence answer shouldn't be allowed to become a long essay, and a step whose consumer is code should return JSON. Use provider prompt caching by putting stable content (system prompt, tool definitions, policy summaries) at the front of the prompt. Cached reads are billed at a steep discount, about 90% off base input price on Anthropic and at least 50% on OpenAI depending on model, and cut time-to-first-token substantially for long prefixes. Cache application results too: retrieval results, repeated policy lookups and tool metadata.

Enforce scope early. Out-of-scope requests that reach your expensive reasoning step burn tokens and tool calls for nothing, so cheap filters, rules and an intent gate should run first. Move non-blocking work such as evaluations, summaries and memory writes off the critical path, batched and run asynchronously. And design for perceived latency. Stream user-facing responses, and show progress states during long tool calls instead of a blank screen.

Finally, measure cost at the level the business cares about: tokens and dollars per step, per conversation, and above all per successful task. An agent that is cheap per call but needs three attempts and a human escalation to finish a task costs more than its per-call price suggests.

14Shipping and changing safely

An agent's behavior is defined by the combination of model version, prompts, tool schemas, retrieval configuration and policy code, so changing any one of them ships a new product. Treat that bundle as a single versioned artifact, tag every trace with it, and roll it out the way you'd roll out a risky backend change: offline evals first, then shadow traffic, then a small canary with automatic rollback on metric regressions, then the full release.

Expect drift even when you change nothing. Providers update and retire models. Your knowledge base changes. Users discover new ways to phrase things. Re-run the regression suite on a schedule, watch the production metrics from Section 11 for trend breaks, and keep a pinned, tested fallback for the day your primary model is deprecated.

Plan governance during design instead of leaving it for a post-launch review. Keep audit trails of who approved which action and when. Know your data residency and your providers' retention terms. Map the system against regulations that apply to your domain: health data, financial services, and the EU AI Act's obligations as they phase in. Write down the autonomy level of each action (suggest only, act with approval, or act autonomously) and the metric threshold that would justify moving it up. Then "can we trust the agent with this?" can be answered from a dashboard.

Last, define success in business terms before you build. What counts as a completed task? What error rate is acceptable for this workflow? What is the target cost per task compared with the current manual process? Without those numbers you can tell that the agent is running, but you can't tell whether it's working.

∎The takeaway

The model is the most impressive component in an agentic system and the least predictable one. Most of the design work is about containing that unpredictability. Give the model the decisions that need language and judgment, and surround it with typed contracts, deterministic policy, durable state, hard budgets, narrow credentials and an evaluation loop that watches every step.

With that structure in place you can safely give the model more autonomy over time, because every increase is bounded, observable and reversible, and the agent that demoed well becomes one people can depend on.
